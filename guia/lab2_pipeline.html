1

Ingesta desde S3 con un stage y COPY INTO

~2 min
SQL
En este paso: Traemos el menu de Tasty Bytes desde S3 a una tabla con un stage y COPY INTO, la base de todo pipeline.
Criterio de exito: COPY INTO carga 100 filas en raw_pos.menu_staging.

Tasty Bytes recibe su menu como archivos CSV en un bucket de S3. Trabajamos como tb_data_engineer, el rol que construye pipelines, con su warehouse tb_de_wh.

SQLContexto
-- Cambia al rol de trabajo
USE ROLE tb_data_engineer;
USE DATABASE tb_101;
USE WAREHOUSE tb_de_wh;
Que deberias ver

Tres mensajes Statement executed successfully.

Un stage es un puntero a una ubicacion de archivos (aqui un bucket publico de S3) junto con el file format que indica como leerlos. LIST muestra los archivos que Snowflake ve en esa ubicacion, sin cargarlos todavia.

SQLStage externo
-- Crea el stage externo apuntando a S3
CREATE OR REPLACE STAGE raw_pos.menu_stage
    COMMENT = 'Stage del menu de Tasty Bytes'
    URL = 's3://sfquickstarts/frostbyte_tastybytes/raw_pos/menu/'
    FILE_FORMAT = public.csv_ff;

-- Lista los archivos del stage
LIST @raw_pos.menu_stage;
Que deberias ver

Stage area MENU_STAGE successfully created. y luego el listado con el archivo menu.csv.gz (nombre, tamano, md5, fecha).

Creamos la tabla de staging. Fijate en la ultima columna: menu_item_health_metrics_obj es de tipo VARIANT, el tipo nativo de Snowflake para datos semi-estructurados (JSON). Luego COPY INTO carga en paralelo todos los archivos del stage.

SQLTabla de staging y carga
-- Crea la tabla
CREATE OR REPLACE TABLE raw_pos.menu_staging
(
    menu_id NUMBER(19,0),
    menu_type_id NUMBER(38,0),
    menu_type VARCHAR,
    truck_brand_name VARCHAR,
    menu_item_id NUMBER(38,0),
    menu_item_name VARCHAR,
    item_category VARCHAR,
    item_subcategory VARCHAR,
    cost_of_goods_usd NUMBER(38,4),
    sale_price_usd NUMBER(38,4),
    menu_item_health_metrics_obj VARIANT
);

-- Carga los datos desde el stage a la tabla
COPY INTO raw_pos.menu_staging FROM @raw_pos.menu_stage;

-- Revisa los datos resultantes
SELECT * FROM raw_pos.menu_staging LIMIT 10;
Que deberias ver

COPY INTO reporta el archivo menu.csv.gz con estado LOADED y 100 filas cargadas. El SELECT muestra 10 items del menu con su JSON de metricas de salud en la ultima columna.

2

JSON nativo con VARIANT y LATERAL FLATTEN

~1 min
SQL
En este paso: Leemos JSON como VARIANT y lo aplanamos con FLATTEN para convertir datos semi-estructurados en columnas utilizables.
Criterio de exito: El ultimo query devuelve una fila por ingrediente de cada item del menu.

Las metricas de salud llegan como JSON. Con VARIANT no necesitas definir un esquema antes: navegas el documento con : (campo), [ ] (posicion en un arreglo) y :: (cast a un tipo SQL). Primero miramos el JSON crudo y luego extraemos el id y el arreglo de ingredientes.

SQLNavegar el JSON
-- Consulta los datos
SELECT menu_item_health_metrics_obj FROM raw_pos.menu_staging LIMIT 5;

-- Aplana el JSON en columnas
SELECT
    menu_item_name,
    menu_item_health_metrics_obj:menu_item_id::INTEGER                       AS menu_item_id,
    menu_item_health_metrics_obj:menu_item_health_metrics[0]:ingredients::ARRAY AS ingredientes
FROM raw_pos.menu_staging;
Que deberias ver

5 documentos JSON con menu_item_id y menu_item_health_metrics; luego 100 filas con MENU_ITEM_NAME, MENU_ITEM_ID e INGREDIENTES como arreglo.

LATERAL FLATTEN explota un arreglo en filas: cada ingrediente pasa a ser una fila propia, unida a su item del menu. Es la pieza clave para transformar JSON en tablas relacionales.

SQLFLATTEN
-- FLATTEN: una fila por cada ingrediente
SELECT
    m.menu_item_name,
    i.value::STRING AS ingrediente
FROM raw_pos.menu_staging m,
     LATERAL FLATTEN(INPUT => m.menu_item_health_metrics_obj:menu_item_health_metrics[0]:ingredients::ARRAY) i
LIMIT 20;
Que deberias ver

20 filas: el mismo MENU_ITEM_NAME se repite una vez por cada INGREDIENTE.

3

Dynamic Table de ingredientes que se refresca sola

~2 min
SQL
En este paso: Creamos una Dynamic Table que se mantiene actualizada sola, sin programar tareas ni orquestadores.
Criterio de exito: Tras el REFRESH aparecen French Baguette y Pickled Daikon con menu_ids [157].

Una Dynamic Table (DT) es un pipeline declarativo: escribes el SELECT con el resultado que quieres y Snowflake mantiene la tabla actualizada de forma automatica e incremental. TARGET_LAG = '1 minute' indica que tan frescos deben estar los datos respecto a la fuente. Esta DT agrupa los ingredientes unicos con la lista de items que los usan.

SQLDT harmonized.ingredient
-- Crea la Dynamic Table que se refresca sola
CREATE OR REPLACE DYNAMIC TABLE harmonized.ingredient
    TARGET_LAG = '1 minute'
    WAREHOUSE = tb_de_wh
AS
SELECT
    i.value::STRING          AS ingredient_name,
    ARRAY_AGG(m.menu_item_id) AS menu_ids
FROM raw_pos.menu_staging m,
     LATERAL FLATTEN(INPUT => m.menu_item_health_metrics_obj:menu_item_health_metrics[0]:ingredients::ARRAY) i
GROUP BY i.value::STRING;

-- Revisa los datos resultantes
SELECT * FROM harmonized.ingredient LIMIT 20;
Que deberias ver

Dynamic table INGREDIENT successfully created. y 20 filas con INGREDIENT_NAME y MENU_IDS (arreglo de ids).

Ahora el negocio cambia: la marca Better Off Bread lanza un Banh Mi con ingredientes nuevos. Insertamos el item en la tabla fuente. La DT lo incorporaria sola dentro de su TARGET_LAG; para no esperar el minuto, forzamos el refresco y buscamos los ingredientes nuevos.

SQLNuevo item y refresco
-- Better Off Bread lanza un Banh Mi con ingredientes nuevos
INSERT INTO raw_pos.menu_staging
SELECT 10101, 15, 'Sandwiches', 'Better Off Bread', 157, 'Banh Mi', 'Main', 'Cold Option', 9.0, 12.0,
PARSE_JSON('{
  "menu_item_health_metrics": [{
      "ingredients": ["French Baguette","Mayonnaise","Pickled Daikon","Cucumber","Pork Belly"],
      "is_dairy_free_flag": "N", "is_gluten_free_flag": "N",
      "is_healthy_flag": "Y", "is_nut_free_flag": "Y"
  }],
  "menu_item_id": 157
}');

-- Esperar ~1 minuto (TARGET_LAG) o forzar el refresco:
ALTER DYNAMIC TABLE harmonized.ingredient REFRESH;

-- Revisa los datos resultantes
SELECT * FROM harmonized.ingredient
WHERE ingredient_name IN ('French Baguette', 'Pickled Daikon');
Momento wow: la Dynamic Table se refresca sola

No hay tareas ni orquestador: defines el resultado y Snowflake mantiene la tabla al dia dentro del TARGET_LAG.

Que deberias ver

number of rows inserted: 1. El REFRESH reporta insertedRows: 5 y el SELECT devuelve French Baguette y Pickled Daikon con MENU_IDS [157].

4

DTs encadenadas: consumo de ingredientes por camion

~2 min
SQL
En este paso: Encadenamos Dynamic Tables para calcular el consumo de ingredientes por camion y vemos como se propagan los cambios.
Criterio de exito: El query final muestra los ingredientes del camion 15 en enero, incluido el Banh Mi.

Las DTs pueden leer de otras DTs y formar una cadena (un DAG): los cambios fluyen solos desde la fuente hasta el resultado final. Esta segunda DT relaciona cada ingrediente con cada item del menu y depende de harmonized.ingredient.

SQLDT de lookup
-- Segunda DT: ingrediente -> item del menu (depende de la anterior)
CREATE OR REPLACE DYNAMIC TABLE harmonized.ingredient_to_menu_lookup
    TARGET_LAG = '1 minute'
    WAREHOUSE = tb_de_wh
AS
SELECT
    i.ingredient_name,
    m.menu_item_health_metrics_obj:menu_item_id::INTEGER AS menu_item_id
FROM raw_pos.menu_staging m,
     LATERAL FLATTEN(INPUT => m.menu_item_health_metrics_obj:menu_item_health_metrics[0]:ingredients) f
JOIN harmonized.ingredient i ON f.value::STRING = i.ingredient_name;
Que deberias ver

Dynamic table INGREDIENT_TO_MENU_LOOKUP successfully created.

Simulamos una venta: una orden de 2 Banh Mi en el camion 15, con su cabecera (order_header) y su detalle (order_detail).

La tercera DT calcula el consumo mensual de ingredientes por camion en Estados Unidos y une unas ~670M lineas de ordenes. Le damos musculo temporal al warehouse (LARGE), creamos la DT y lo devolvemos a XSMALL: el computo es elastico y solo pagas lo que usas.

SQLDT final con warehouse LARGE
-- Tercera DT: consumo mensual de ingredientes por camion (US).
-- Une ~670M lineas: le damos musculo temporalmente al warehouse
ALTER WAREHOUSE tb_de_wh SET WAREHOUSE_SIZE = 'large';

-- Crea la Dynamic Table que se refresca sola
CREATE OR REPLACE DYNAMIC TABLE harmonized.ingredient_usage_by_truck
    TARGET_LAG = '2 minutes'
    WAREHOUSE = tb_de_wh
AS
SELECT
    oh.truck_id,
    EXTRACT(YEAR FROM oh.order_ts) AS order_year,
    MONTH(oh.order_ts)             AS order_month,
    i.ingredient_name,
    SUM(od.quantity)               AS total_ingredients_used
FROM raw_pos.order_detail od
JOIN raw_pos.order_header oh               ON od.order_id = oh.order_id
JOIN harmonized.ingredient_to_menu_lookup iml ON od.menu_item_id = iml.menu_item_id
JOIN harmonized.ingredient i               ON iml.ingredient_name = i.ingredient_name
JOIN raw_pos.location l                    ON l.location_id = oh.location_id
WHERE l.country = 'United States'
GROUP BY oh.truck_id, order_year, order_month, i.ingredient_name;

-- Devuelve el warehouse a XSmall
ALTER WAREHOUSE tb_de_wh SET WAREHOUSE_SIZE = 'xsmall';
Que deberias ver

Dynamic table INGREDIENT_USAGE_BY_TRUCK successfully created. en ~9 s con el warehouse en LARGE; luego Statement executed successfully. al volver a XSMALL.

Operaciones ya puede responder: que ingredientes necesita comprar el camion 15 para enero?

SQLIngredientes del camion 15
-- Ingredientes que necesita el camion 15 en enero (incluye el Banh Mi)
SELECT truck_id, order_year, ingredient_name, SUM(total_ingredients_used) AS total_usado
FROM harmonized.ingredient_usage_by_truck
WHERE order_month = 1 AND truck_id = 15
GROUP BY ALL
ORDER BY total_usado DESC;
Que deberias ver

Camion 15, enero: Hoagie Roll 5,835 y Lettuce 5,835 (2022) en la parte alta; los ingredientes del Banh Mi (French Baguette, Pickled Daikon...) aparecen con 2 unidades.
