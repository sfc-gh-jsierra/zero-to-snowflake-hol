2

RBAC: un rol de Data Steward

~1 min
SQL
En este paso: Creamos un rol de Data Steward con permisos minimos y vemos que hoy los datos personales de clientes estan expuestos.
Criterio de exito: Se crea tb_data_steward y, con ese rol, ves nombres, emails y telefonos en claro.

En Snowflake los permisos se dan a roles y los roles a usuarios (RBAC, Role-Based Access Control). Cada rol de sistema tiene su funcion: useradmin crea roles y usuarios; securityadmin administra grants.

SQLCrear el rol
-- useradmin es el rol que crea roles
USE ROLE useradmin;
-- Crea el rol de Data Steward
CREATE OR REPLACE ROLE tb_data_steward COMMENT = 'Data Steward de Tasty Bytes';
Que deberias ver

Role TB_DATA_STEWARD successfully created.

Gotcha real: useradmin no puede USE DATABASE

useradmin no tiene acceso a la base, asi que el lab arranca con accountadmin (para el USE DATABASE y la limpieza) y solo cambia a useradmin para crear el rol.

Con securityadmin damos al steward computo (tb_dev_wh), acceso a la base y esquemas, lectura de los clientes y control total del esquema governance.

SQLGrants
-- securityadmin administra los permisos
USE ROLE securityadmin;
-- Permisos del steward: computo, base, esquemas y clientes
GRANT OPERATE, USAGE ON WAREHOUSE tb_dev_wh TO ROLE tb_data_steward;
GRANT USAGE ON DATABASE tb_101 TO ROLE tb_data_steward;
GRANT USAGE ON ALL SCHEMAS IN DATABASE tb_101 TO ROLE tb_data_steward;
GRANT SELECT ON ALL TABLES IN SCHEMA tb_101.raw_customer TO ROLE tb_data_steward;
GRANT ALL ON SCHEMA tb_101.governance TO ROLE tb_data_steward;
Que deberias ver

Cada grant: Statement executed successfully.

Asignamos el rol a tu usuario (con una variable de sesion) y a sysadmin, siguiendo la buena practica de que toda jerarquia de roles cuelgue de sysadmin.

SQLAsignar el rol
-- Guarda tu usuario en una variable de sesion
SET my_user = CURRENT_USER();
-- Asigna el rol a tu usuario
GRANT ROLE tb_data_steward TO USER IDENTIFIER($my_user);
-- Cuelga el rol de sysadmin (buena practica)
GRANT ROLE tb_data_steward TO ROLE sysadmin;
Que deberias ver

Statement executed successfully.

3

Clasificacion automatica de PII

~2 min
SQL
En este paso: Dejamos que Snowflake detecte y etiquete automaticamente los datos personales, sin revisar columna por columna.
Criterio de exito: TAG_REFERENCES_ALL_COLUMNS lista las columnas tagueadas con governance.pii, incluida BIRTHDAY_DATE.

Un tag es metadata que se adjunta a objetos o columnas. Como accountadmin creamos el tag pii y damos al steward los privilegios de aplicar tags y masking policies a nivel de cuenta.

SQLTag y privilegios de aplicar
-- Vuelve a accountadmin para crear el tag
USE ROLE accountadmin;
-- Crea el tag pii para marcar columnas sensibles
CREATE OR REPLACE TAG governance.pii;
-- Permite al steward aplicar tags y masking
GRANT APPLY TAG ON ACCOUNT TO ROLE tb_data_steward;
GRANT APPLY MASKING POLICY ON ACCOUNT TO ROLE tb_data_steward;
Que deberias ver

Tag PII successfully created. y grants exitosos.

Mas privilegios: aplicar row access policies, ejecutar clasificacion automatica, el rol de base CLASSIFICATION_ADMIN y crear perfiles de clasificacion en governance.

SQLPrivilegios de clasificacion
-- Permisos de row policies y clasificacion automatica
GRANT APPLY ROW ACCESS POLICY ON ACCOUNT TO ROLE tb_data_steward;
GRANT EXECUTE AUTO CLASSIFICATION ON SCHEMA raw_customer TO ROLE tb_data_steward;
GRANT DATABASE ROLE SNOWFLAKE.CLASSIFICATION_ADMIN TO ROLE tb_data_steward;
GRANT CREATE SNOWFLAKE.DATA_PRIVACY.CLASSIFICATION_PROFILE ON SCHEMA governance TO ROLE tb_data_steward;
Que deberias ver

Statement executed successfully. en los 4 grants.

Snowflake detecta PII (Personally Identifiable Information) por ti. Un perfil de clasificacion define como clasificar; con auto_tag: true aplica tags automaticamente. SET_TAG_MAP dice: toda columna clasificada como nombre, telefono, codigo postal, fecha de nacimiento, ciudad o email recibe el tag pii.

SQLPerfil y mapa de tags
-- Vuelve al rol de Data Steward
USE ROLE tb_data_steward;
-- Crea el perfil de clasificacion con auto tag
CREATE OR REPLACE SNOWFLAKE.DATA_PRIVACY.CLASSIFICATION_PROFILE governance.tb_classification_profile(
    {'minimum_object_age_for_classification_days': 0,
     'maximum_classification_validity_days': 30,
     'auto_tag': true});

-- Toda columna clasificada como nombre/telefono/email/etc. recibe el tag PII
CALL governance.tb_classification_profile!SET_TAG_MAP(
  {'column_tag_map':[{
      'tag_name':'tb_101.governance.pii',
      'tag_value':'pii',
      'semantic_categories':['NAME','PHONE_NUMBER','POSTAL_CODE','DATE_OF_BIRTH','CITY','EMAIL']}]});
Que deberias ver

Perfil creado y el CALL responde sin error.

SYSTEM$CLASSIFY analiza la tabla con el perfil y aplica los tags. Luego consultamos que columnas quedaron tagueadas.

SQLClasificar y revisar
-- Clasifica la tabla de clientes y aplica tags
CALL SYSTEM$CLASSIFY('tb_101.raw_customer.customer_loyalty', 'tb_101.governance.tb_classification_profile');

-- Que encontro la IA de clasificacion?
SELECT column_name, tag_name, tag_value, apply_method
FROM TABLE(INFORMATION_SCHEMA.TAG_REFERENCES_ALL_COLUMNS('raw_customer.customer_loyalty', 'table'))
ORDER BY column_name;
Que deberias ver

Filas con TAG_NAME = PII para las columnas sensibles (nombres, email, telefono, ciudad, codigo postal y BIRTHDAY_DATE).

4

Masking dinamico basado en tags

~1 min
SQL
En este paso: Ocultamos los datos personales segun el rol con una sola regla sobre el tag, que protege columnas actuales y futuras.
Criterio de exito: Como tb_analyst ves ****MASKED**** y cumpleanos truncados al anio; como tb_admin, en claro.

Una masking policy decide en tiempo de consulta que ve cada rol. Creamos dos (texto y fecha) y las asociamos una sola vez al TAG, no columna por columna.

SQLPolicies sobre el tag
-- Enmascara texto salvo para roles administradores
CREATE OR REPLACE MASKING POLICY governance.mask_string_pii AS (val STRING) RETURNS STRING ->
    CASE WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN', 'TB_ADMIN') THEN val
         ELSE '****MASKED****' END;

-- Deja solo el anio de las fechas sensibles
CREATE OR REPLACE MASKING POLICY governance.mask_date_pii AS (val DATE) RETURNS DATE ->
    CASE WHEN CURRENT_ROLE() IN ('ACCOUNTADMIN', 'TB_ADMIN') THEN val
         ELSE DATE_TRUNC('year', val) END;

-- Una sola vez sobre el TAG: protege todas las columnas PII, hoy y manana
ALTER TAG governance.pii SET
    MASKING POLICY governance.mask_string_pii,
    MASKING POLICY governance.mask_date_pii;
Que deberias ver

Dos policies creadas y Statement executed successfully. en el ALTER TAG.

La misma consulta con dos roles distintos.

SQLComparar roles
-- Consulta como analista: veras PII enmascarada
USE ROLE tb_analyst;
USE WAREHOUSE tb_analyst_wh;
SELECT TOP 10 customer_id, first_name, last_name, e_mail, phone_number, birthday_date, country
FROM raw_customer.customer_loyalty;

-- Misma consulta como admin: veras datos en claro
USE ROLE tb_admin;
SELECT TOP 10 customer_id, first_name, last_name, e_mail, phone_number, birthday_date, country
FROM raw_customer.customer_loyalty;
Que deberias ver

Como tb_analyst: nombres/email/telefono = ****MASKED****, cumpleanos 1953-12-01 se ve 1953-01-01. Como tb_admin: Rodolfo Tucker, Rodolfo.Tucker@ymail.com.

Momento wow: masking por TAG

La policy vive en el tag: protege todas las columnas PII que existen hoy y cualquier columna futura que reciba el tag, sin tocar tabla por tabla.

5

Row Access Policy por rol

~1 min
SQL
En este paso: Limitamos que filas ve cada rol segun el pais, para que cada equipo vea solo los clientes que le corresponden.
Criterio de exito: tb_data_engineer solo ve United States; tb_analyst ve todos los paises.

Seguridad a nivel de fila: una tabla de mapeo rol → pais, creada por el steward.

SQLTabla de mapeo
-- Contexto: steward con su warehouse
USE ROLE tb_data_steward;
USE WAREHOUSE tb_dev_wh;
-- Tabla de mapeo rol a pais permitido
CREATE OR REPLACE TABLE governance.row_policy_map (role STRING, country_permission STRING);
-- El data engineer solo vera Estados Unidos
INSERT INTO governance.row_policy_map VALUES ('TB_DATA_ENGINEER', 'United States');
Que deberias ver

Tabla creada y number of rows inserted: 1.

La Row Access Policy devuelve TRUE/FALSE por fila: los roles administrativos y el analista ven todo; el resto, solo los paises de su mapeo. Se asocia a la columna country.

SQLCrear y asociar la policy
-- Decide fila por fila que paises ve cada rol
CREATE OR REPLACE ROW ACCESS POLICY governance.customer_loyalty_policy
AS (country STRING) RETURNS BOOLEAN ->
    CURRENT_ROLE() IN ('ACCOUNTADMIN', 'SYSADMIN', 'TB_ADMIN', 'TB_ANALYST')
    OR EXISTS (SELECT 1 FROM governance.row_policy_map rp
               WHERE rp.role = CURRENT_ROLE() AND rp.country_permission = country);

-- Aplica la politica sobre la columna country
ALTER TABLE raw_customer.customer_loyalty
    ADD ROW ACCESS POLICY governance.customer_loyalty_policy ON (country);
Que deberias ver

Policy creada y asociada sin error.

SQLComparar roles
-- Prueba como data engineer
USE ROLE tb_data_engineer;
-- solo US
SELECT country, COUNT(*) AS clientes FROM raw_customer.customer_loyalty GROUP BY country;

-- Prueba como analista
USE ROLE tb_analyst;
-- solo US
SELECT country, COUNT(*) AS clientes FROM raw_customer.customer_loyalty GROUP BY country;
Que deberias ver

tb_data_engineer: 1 fila, United States con 46,300 clientes. tb_analyst: todos los paises.

Momento wow: RLS por rol

Mismo SQL, misma tabla, resultados distintos: el filtro lo aplica Snowflake segun el rol, no la aplicacion.

6

Calidad de datos con DMFs

~2 min
SQL
En este paso: Medimos la calidad de los datos (nulos, duplicados, emails invalidos) y dejamos un monitoreo automatico ante cada cambio.
Criterio de exito: Obtienes % de emails nulos, IDs duplicados y emails invalidos; la DMF propia queda asociada con TRIGGER_ON_CHANGES.

Las Data Metric Functions (DMF) miden la calidad de los datos. Snowflake trae DMFs de sistema en SNOWFLAKE.CORE. Cambiamos a sysadmin, el duenio de las tablas.

SQLDMFs de sistema
-- Contexto: sysadmin con warehouse de desarrollo
USE ROLE sysadmin;
USE WAREHOUSE tb_dev_wh;
-- DMFs de sistema
SELECT SNOWFLAKE.CORE.NULL_PERCENT(SELECT e_mail FROM raw_customer.customer_loyalty)      AS pct_email_nulo;
-- Cuenta ids de cliente duplicados
SELECT SNOWFLAKE.CORE.DUPLICATE_COUNT(SELECT customer_id FROM raw_customer.customer_loyalty) AS ids_duplicados;
Que deberias ver

Una fila con PCT_EMAIL_NULO y otra con IDS_DUPLICADOS.

Tambien puedes crear una DMF propia: esta cuenta emails con formato invalido usando una expresion regular.

SQLDMF propia
-- DMF propia: emails con formato invalido
CREATE OR REPLACE DATA METRIC FUNCTION governance.invalid_email_count(t TABLE(email STRING))
RETURNS NUMBER AS
'SELECT COUNT_IF(email IS NOT NULL AND NOT REGEXP_LIKE(email, ''^[^@]+@[^@]+\\.[^@]+$'')) FROM t';

-- Ejecuta la DMF propia sobre los emails
SELECT governance.invalid_email_count(SELECT e_mail FROM raw_customer.customer_loyalty) AS emails_invalidos;
Que deberias ver

Funcion creada y una fila con EMAILS_INVALIDOS.

Para monitoreo continuo, programamos la tabla para evaluar sus DMFs cada vez que cambie y le asociamos la nuestra sobre e_mail.

SQLMonitoreo automatico
-- Monitoreo automatico cada vez que cambie la tabla
ALTER TABLE raw_customer.customer_loyalty SET DATA_METRIC_SCHEDULE = 'TRIGGER_ON_CHANGES';
-- Asocia la DMF de emails a la columna e_mail
ALTER TABLE raw_customer.customer_loyalty
    ADD DATA METRIC FUNCTION governance.invalid_email_count ON (e_mail);
Que deberias ver

Statement executed successfully. en ambos.

Gotcha real: asociar DMFs requiere OWNERSHIP

Asociar una DMF a una tabla exige ser duenio de la tabla. Por eso esta parte corre con sysadmin, el duenio de las tablas.

Verlo en la UI

Revisa los resultados en Catalog > TB_101 > RAW_CUSTOMER > CUSTOMER_LOYALTY, pestana Data Quality.

7

Trust Center: seguridad de la cuenta

~1 min
UI
En este paso: Activamos el Trust Center para detectar riesgos de seguridad de la cuenta, como usuarios sin MFA, y ver como corregirlos.
Criterio de exito: Habilitas un scanner package y abres el detalle de un hallazgo en Findings.

El Trust Center es un dashboard central de riesgos de seguridad: scanners programados detectan, por ejemplo, usuarios sin MFA, roles con exceso de privilegios o usuarios inactivos, y proponen como remediarlo. Hazlo con el rol ACCOUNTADMIN en Snowsight.

  1. En el menu izquierdo ve a Governance & Security > Trust Center.
  2. Abre la pestana Scanner Packages y haz clic en CIS Benchmarks.
  1. Pulsa Enable Package.
  1. En el modal, deja Frequency en Monthly y pulsa Continue. Opcional: repite con Threat Intelligence.
  1. Tras unos minutos vuelve a la pestana Findings: veras las violaciones por severidad. Haz clic en una para ver su resumen y la remediacion recomendada.
Si aun no hay hallazgos

Los scanners tardan un poco en correr la primera vez. Si no aparecen en el tiempo del lab, revisalo despues: el paquete queda habilitado.
